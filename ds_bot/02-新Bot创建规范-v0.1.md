# 02 · 新 Bot 创建规范 v0.1

状态：已生效（2026-10-13）· 主责：Chief · 依据：`01-设计意图-源自ds-bot作者.md`
适用范围：**任何新建 Bot**（含复制已有 Bot）。建 Bot 是 Main Bot 独占权限，由 Chief 执行。

---

## 0. 先问三个问题（不该建就别建）

1. **它是不是一个"长期的人"？** ds-bot 的 Bot 是常驻 Session（作者原话 "long-lived Bots"）。一次性的活、并行的调研、可丢的试验——用 subagent / workflow，不要占编制。
2. **现有岗位能不能干？** `plan_bots` 里已有的岗位优先复用；做不到再加人，**不加重复岗位**。
3. **它有边界吗？** 说不清"能写哪些文件、禁止做什么、向谁汇报"的岗位，先别建。

## 0.1 建人阈值（量化，2026-10-13 补录）

常驻 Bot 只在这些条件**至少满足一条**时才建：

1. 该职责**重复出现 ≥3 次**（不是一次性的活）；
2. 它需要**独立记忆**（跨会话积累）；
3. 它需要**独立写权**（有自己的文件范围，不能与别人共用）。

否则走这两条路：**临时工（subagent）**——一次性的活即时派、做完即散、不进编制、不写名册；或**复用现有岗位**。
补充：闲置的常驻 Bot 零成本（不发消息就不烧 token），**不要为"省资源"去删人**。

## 1. 建之前：查重

- `list_bots` 看现有 Bot、角色、模型与群；避免同名、同职能重复建。
- 名字唯一（插件会拒绝重名）；岗位标签 ≤24 字符。

## 2. 命名与标签

| 字段 | 规则 |
| --- | --- |
| `name` | ≤40 字符，短、好叫、能被人 `@`；岗位化命名（如"项目经理""数据工程师"） |
| `role` | ≤24 字符的角色标签（如 `PM`、`Data`、`QA`），给人看 |
| 颜色/头像 | 仅在用户明确要时设置 |

## 3. `instructions` 怎么写（公司级岗位卡模板）

**五段固定结构，且绝对不写项目事实：**

```
你是什么岗位（公司级、跨项目复用，不绑定任何单一项目）。

项目加载协议（每次派工照做）：
1. 派工消息会给出项目根目录或项目名；先读该项目的 PROJECT-CARD.md 与 AGENTS.md；
   没有档案卡就先向派工方索取，不要自行全盘扫描。
2. 按档案卡给出的索引、写权白名单、运行环境与硬约束工作。
3. 项目记忆按项目 topic 隔离；禁止把 A 项目的结论带到 B 项目。

职责：3-6 条，可检查的行为，不是口号。

边界：可写范围（规则级，不是具体路径）、需上报事项、禁止事项。

汇报：项目事项向项目经理；资源/模型事项向 Chief。

团队通用硬约束：只追加不覆盖历史；令牌与账户标识零落盘；任何「等外部返回」都要有超时上界；
结论标注证据强度；性能数字复测或标注「单次观测」；探针与脚本改动走 TDD，真跑前先干跑。
```

## 4. 模型怎么选

- 一次只分配一个模型（插件就是"每个 Bot 一个模型"）。
- 遵守网关并发约束：不同网关的并行上限不同（从 1 个到 3-4 个不等），部分路由只在特定时段够用；**受限的模型不常驻**，并发不受限的轻模型优先承接文档类任务。
- **切换模型前先验该路由有凭据**（有过一次 no API key 的教训），必要时先跑一次最小合成请求。
- 受限模型不常驻；重任务给强模型，文档类轻任务给 `<模型D>`。

## 5. 记忆与项目知识

- **岗位知识**（手艺、经验教训）→ 该 Bot 自己的记忆。
- **团队级事实**（模型分配、网关约束、协作规则）→ team memory（Main Bot 写）。
- **项目知识** → 记忆 `topic`（`<项目名>`、`bot-mgmt`、…），并在项目档案卡里留索引。
- **绝不**把项目路径、阶段、测试数写进 `instructions`（原因见 01 文档 §6：会腐烂 + 破坏提示词前缀缓存）。

## 6. 群与协作

- 有项目就进对应的项目群（如「<项目组>」）；群公告写项目边界与汇报线。
- 需要用户直接读到某 Bot 的汇报时，用 `message_bot(reply_to="user")`，不要让 Chief 转述。
- 群列表与成员变动由 Chief 维护；群管理员权限只给自己的群。

## 7. 创建后动作（回执，必做）

1. 用一行告诉用户：**它叫什么、一句话职责、用的哪个模型、进了哪个群**。
2. 在工作区项目注册表 `projects.md` 中确认它有归属项目；若无项目，登记到 bot管理项目名下。
3. 若引入了新的记忆 `topic`，在团队记忆里留一条索引。

## 8. 反模式清单（明确禁止）

| 反模式 | 后果 |
| --- | --- |
| 把项目路径/阶段/测试数写进 `instructions` | 数据腐烂；身份段前缀缓存失效 |
| 为一次性任务建 Bot | 占编制、占网关闭发位、增加协调成本 |
| 多个常驻 Bot 挤同一个受限路由 | 排队、超时，被误判成"上游坏了" |
| 建重复岗位（同一职责两个 Bot） | 汇报打架、文件抢写 |
| 让 Bot 拥有 Main Bot 权限 | 组织变更失控（权限表里 Main Bot 可改/删 Bot） |
| 建完不说 | 用户不知道团队变了 |

## 9. 变更与退役

- **共享文本（群公告、团队文档）必须先读原文、再追加改**。**禁止凭记忆整段重写**：那不是"只追加"，会覆盖掉别的会话（含群里那个你）写进去的内容，而且事后无法从状态文件区分"没写过"和"被覆盖了"。已发生过一次疑似事故（见 `04-Bot合规体检-2026-10-13.md` F5）。
- **改 `instructions` = 会让该 Bot 的提示词前缀缓存整体失效**。改前想清楚，改后告知用户影响。
- 改模型/改名前先确认没有正在跑的 turn；必要时 `stop_bot`。
- 退役：不能直接删除时，先把职责与在办任务交接给接任岗位，再改名/回收（插件删 Bot 会归档其记忆）。

## 10. 检查清单（建 Bot 前逐项过）

- [ ] 确认是"长期的人"，不是一次性任务
- [ ] `list_bots` 查重通过
- [ ] 名字与 `role` 合规（≤40 / ≤24）
- [ ] `instructions` 是公司级五段模板，**零项目事实**
- [ ] 模型已按网关约束选定，路由凭据已验证
- [ ] 记忆 `topic` 已规划（项目名），不与别的项目混用
- [ ] 已入对应项目群；群公告边界清楚
- [ ] 创建后已向用户一行回执
