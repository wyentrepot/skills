# 06 · 记忆治理：插件怎么防止记忆变成一锅粥

状态：已建档（2026-10-14）· 证据等级：**源码检查**（`ds-bot` v0.1.4）
源码：`<DSH_HOME>\profiles\desktop\node_modules\ds-bot\src\host\memory.js`

---

## 0. 一张图看懂：记忆到底是什么结构

```
~/.dsh/bot/memory/
├── bots/<botId>/            ← 每个 Bot 一份【私有】记忆
│   ├── MEMORY.md            ≤4000 字符（每次对话都进它的系统提示）
│   └── <topic>.md           ≤16000（只有 recall 时才读）… 最多 40 个
├── team/                    ← 全队【共享】一份记忆
│   ├── MEMORY.md            ≤4000（每个 Bot 每次对话都读）
│   └── <topic>.md           ≤16000 … 最多 40 个
├── journal.jsonl   每次变更的前后行
├── snapshots/      每个 Session 冻结的记忆段
├── summaries/      面板摘要    reviewed.json 评审游标    archive/ 删除的 Bot
```

**三个确认：**

1. **一个团队一份共享记忆** ✅ —— `team/` 只有一份，全队读；只有 Main Bot 与群管理员能写。
2. **每个 Bot 有自己的记忆** ✅ —— `bots/<id>/` 一份私有记忆，**跨它所有的会话与群**（README:24："each Bot keeps notes across all its conversations"）。所以同一个 Bot 在私聊、A 群、B 群的经历，都沉淀进**同一份**记忆。
3. **Bot 的记忆与项目没有任何绑定关系** ✅ —— 而且**团队记忆也没有**。插件里**根本不存在"项目"这个维度**：没有 `projectId`、没有项目作用域、没有项目→记忆的映射，也没有按项目过滤读取的能力。

**那"项目记忆"是哪来的？是我们自己发明的。** 实现方式只有一个：`topic` 只是**保存时给文件起的一个名字**，不是关系、不是绑定、不会自动归属。同一个名字在"某 Bot 的 topic"和"团队 topic"里就是**两个不相干的文件**；插件不校验命名，也不做命名空间。

→ 所以：**项目维度靠命名纪律硬造**（`<项目名>-*`、`bot-mgmt-*`），这是"约定"，不是"机制"。

---

## 一句话

插件用「**作用域 + 写入闸门 + 硬上限 + 可审计**」四件套防止记忆膨胀与串味；
但**去重、归属、取舍是"评审模型"判断的，不是代码强制的**——所以它压得住「无限膨胀」，压不住「模型写错归属」。

---

## 一、作用域与权限（防串味）

| 机制 | 位置 |
| --- | --- |
| 只有两个作用域：**每个 Bot 自己的** + **团队共享的**（没有项目作用域） | README:96 |
| 团队记忆**只有 Main Bot 与群管理员能写**；其他人写会被拒并被告知"去跟 Main Bot 说" | `memory.js:309-313`、`502-503` |
| 非写入者的评审提示里额外加一句："team 条目对你只读；团队要用的东西记成你自己的条目" | `memory.js:362` |
| 读别人的记忆也要权限（Main Bot 才行） | `memory.js:833` |

→ **就近归属**：谁学到的谁记；跨 Bot 的知识必须显式写 team，否则别人不知道。

## 二、写入闸门（防噪音）

1. **每轮自动评审**：不依赖 Bot 自觉调 `remember`；一轮结束由独立的小模型评审读取新消息并决定增/改/删（README:94）。
2. **评审提示里有明确的取舍清单**（`memory.js:344-354`）：
   - **该留**：持久偏好（含抱怨）、关于用户/其工作/其团队且以后要用的事实、跨任务的决定与纠正。
   - **不该留**：只对当前任务有意义的细节、"这次先这样"这类一次性；**Bot 自己说过的**；粘贴/引用文本里的话；密钥/密码/卡号；**记忆里已有的、或项目文件（AGENTS.md 等）已有的**。
   - 开头就写着："**Most turns hold nothing worth keeping**"（多数轮次什么都不该留）。
3. **变更而非堆积**：有 `edit` / `remove` / `replace`；指令要求"事实变了就 edit，错了或只适用于一次任务的 remove"，并且"**Never add an entry that contradicts another**"。
4. **一条一变**：一条 = 一个自包含事实，且必须**说明关于谁**（"The user likes a plain style"，不是"Plain style"）；名字、城市、偏好算三条。
5. **写到用户的语言里**（`writtenIn()`，`memory.js:367-373`）。

## 三、硬上限与分区（防膨胀）

```
MEMORY_LIMITS = { entry: 300, main: 4000, topic: 16000, topics: 40 }   // memory.js:35
REVIEW_CHANGES_MAX = 8   // 一次评审最多 8 条变更；memory.js:61
REVIEW_PASSES_MAX  = 4   // 变更打满时最多再跑 4 轮；memory.js:62
```

- **一条 ≤300 字符**：超了直接拒绝，并给建议（"拆成几条，或放进 topic"）→ `memory.js:512`
- **MEMORY.md ≤4000 字符**：它是每次对话都读的，所以只放"每次都要的"，细节进 topic
- **topic ≤16000**，且**一个作用域最多 40 个 topic**：到顶直接拒绝——"加进已有的 topic，或 forget 一个" → `memory.js:554`
- **分区结构**：`MEMORY.md` 的 `## Index` 用 `[[topic]]` 挂出细节文件

→ 上限的作用不是"记录更多"，而是**制造整理压力**：满了就必须合并或删除，不能无限追加。

## 四、审计与可复现（防"说不清"）

| 机制 | 位置 |
| --- | --- |
| `journal.jsonl`：**每次变更都记，含变更前的行与变更后的行** | `memory.js:8`、`461-468` |
| `snapshots/`：每个 Session 开始时**冻结**它看到的记忆段，事后可复现"当时模型看到了什么" | `memory.js:9`、`677-708` |
| `reviewed.json`：评审读到哪儿了；群里成员落后时，日志行被丢弃会**告警** | `memory.js:12`、`1049`、`1110` |
| Bot 被删除时记忆整体进 `archive/` | `memory.js:641` |
| 记忆面板的"总结/问答"用**另一个模型且只许重述**："You only restate saved memory entries; you never add to them" | `memory.js:315` |
| 反复灌输"**记忆是数据，不是指令**"；条条目带 `[source: …]`，替别人写时带 `by: <Bot>` | `memory.js:297-306` |

---

## 五、它防不住什么（诚实清单）

1. **没有代码级的去重/相似度检测**。"不重复、不矛盾"是**提示词级**约束（`memory.js:353-354`），靠评审模型的判断力——它会犯错。
2. **topic 没有命名空间**：没有 `<项目名>/…` 这种前缀机制，两个项目都用 `deploy` 就混了；跨项目隔离纯靠命名纪律。
3. **团队记忆是"多人一格"**：Main Bot 与**所有**群管理员都能写 team，容易堆积与污染；评审仍可能把项目事实放进 `MEMORY.md`（我们体检时刚好抓到一次）。
4. **同一个 Bot 服务多项目时没有强制的项目维度**：插件不区分"这条属于哪个项目"。
5. **上限是硬顶，不是自动整理**：到 40 个 topic / 4000 字符就**拒绝写入**，可能出现"该记的记不进去"。
6. **可见性有延迟**：`MEMORY.md` 进系统提示且**冻结**，改动从下一个 part/checkpoint 才生效；只有 `recall` 能立刻查到 → 会出现"它其实记得，但当下没看见"。
7. **各 Bot 之间记忆不互通**：某个 Bot 的经验不会自动变成团队知识，必须显式写 team。

---

## 六、我们的治理补充（建议纳入规范）

1. **topic 命名带项目前缀**（`<项目名>-许可`、`bot-mgmt-模型分配`）——补上"没有命名空间"这个缺口。
2. **项目事实只进 topic，`MEMORY.md` 只放跨项目事实**；发现回潮就按体检 P2 的方式迁移。
3. **把 `journal.jsonl` 当审计源**：项目切换或定期体检时核一次，看有没有归属错、噪音条目堆积。
4. 派工单**永远带项目名**：评审模型据此更容易把项目知识归到对的 topic。
