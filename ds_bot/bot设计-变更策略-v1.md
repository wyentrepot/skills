# Bot 设计与变更策略 v1（草案）

> **状态：草案，待用户批准。** 本文件放在公开仓库，是该策略的唯一权威版本。
> **依据**：ds-bot 插件（v0.1.5）原生机制 + 2026-10-19 用户逐条决定。
> **边界**：本文件只写岗位无关的通用规则；项目事实（工程根目录、阶段、验收门、测试数）写在各自项目档案里，不进本文件。

---

## 0. 一句话

**一个 req = 一个 Bot = 一条上下文 = 一个工作区。** Bot 是上下文管理的载体，跟着工程走；req 结束，Bot 退役。

---

## 1. 为什么这么设计（插件原生事实，不是我们的发明）

| 原生事实 | 推论 |
| --- | --- |
| 每个 Bot 一条身份段、一份记忆（`<DSH_HOME>\bot\memory\bots\<botId>\`）、一个 `bot.workDir`、一套会话 | **上下文边界的原生单位就是 Bot**，不是群、不是任务 |
| 群会话仍是「每成员各一条」 | 群是**通信/可见性**单位，不是分域单位 |
| 域 = `room.workDir ?? bot.workDir ?? bot 工作区`；换目录即换代（写交接笔记 → 保留最近约 16k → 旧 part 归档） | **分域 = 换目录**；换代是该机制的自然结果，不另造机制 |
| 记忆 per-Bot：`MEMORY.md` ≤4000 字符 + topic ≤16000 × 40 | 一 req 一 Bot ⇒ **req 边界直接等于记忆边界**，天然隔离 |

**历史教训**：v0 把 Bot 当「数字员工」，发明了岗位体系、汇报线、治理规范，已整体作废。**本策略不重演。**

---

## 2. 结构与关系

```
团队 ──1:1── bot 工作区（"家"）      ← 共享 Bot、横向事务落这里
团队 ──1:N── req Bot               ← 一 req 一 Bot；bot.workDir = 该 req 的工程根
团队 ──1:N── 共享 Bot（少量）        ← 横向职能，常驻"家"，不挂任何 req 域
团队 ──1:N── 群                    ← 协作/可见性单位（不承担分域）
                └── 临时工 subagent ← 一次性活，办完即散

域   = room.workDir ?? bot.workDir ?? bot 工作区
记忆 = per-Bot：req Bot 天然隔离；共享 Bot 靠 topic 命名分 req
并发 = 同时最多 4 个 req 活跃
```

---

## 3. 三类"人"

| 类别 | 数量 | 存在期 | 记忆 |
| --- | --- | --- | --- |
| **req Bot** | 每个活跃 req 一个（≤4） | req 建立 → 建成；**完成即停用**（记忆归档） | 天然按 req 隔离 |
| **共享 Bot** | 少量固定 | 长期 | 跨 req，靠 topic 命名分 req |
| **临时工 subagent** | 0 常驻 | 一次性 | 无 |

**设人的判据**（由上下文边界推导，不由"组织像不像"决定）：某职责**需要独立记忆**、**需要独立写权**、或**长期存在**，三者满足其一才设人；否则用会话或 subagent 办完即散。

---

## 4. 命名

- **req Bot**：用 req 命名 → `<项目>-<编号>`（例：`demo-0001`）
- **共享 Bot**：用职能名
- **编号**：沿用项目编号，团队不另起一套；多项目撞号用 **`项目/编号`** 定位（例：`demo/0001`），不新增字段

---

## 5. 指针卡 `CARD.md`（固定 8 字段）

放在 `<bot 工作区>\reqs\<项目>\<编号>\CARD.md`，作用是**让下一个接手的人或模型不用问就能定位**，不存正文。

```yaml
req:      <项目>/<编号>
项目:     一句话的项目名
目标:     一句话：这个需求干什么
分支:     main
工作区:   <工程根目录的绝对路径>
Bot:      <承载它的 Bot 名>
权威文档: <项目仓>\reqs\<编号>-<slug>\
状态:     进行中 | 冻结 | 已完成
```

**权威只有一处**：正文在项目仓（随分支走、可版本化）；指针卡不复制正文，避免分叉。

---

## 6. 记忆纪律

```
MEMORY.md    ≤4000     只放跨 req 的常驻：口径、习惯、身份
topic        ≤16000×40 req 细节，命名 <项目>-<编号>-*，按需 recall
journal/快照            插件自带审计（变更前后 + 每会话冻结）
人可读性                 由 CARD.md + 项目仓文档承担
```

**不在 req 目录另存记忆正文**（双份必分叉）。Bot 的记忆是**跨工作区**的（跟人走），换 req 不丢身份，但 req 细节只落在该 req 的 topic 里。

---

## 7. 索引与检索协议

**团队总表**（脚本自动生成）只做地图，一行一 req：

| 项目 | 编号 | 分支 | 工作区 | Bot | CARD 路径 |
| --- | --- | --- | --- | --- | --- |

**不列状态**——状态是项目仓 `REQS-INDEX.md` 的权威，团队表再写一处就会两边不一致。

- 别名表 `_meta/req-aliases.md`（口语 ↔ req，与索引同目录同版本）
- 经验索引 `经验索引.md`（查完追加一行，满 20 条归档，只追加）
- 检索协议（借 `shared/knowledge-base/knowledge-lookup` 的思路，结构自定）：
  ① **探测优先**（先 grep，不整读索引）
  ② 命中只读那一小节，不整读大文件
  ③ 输出契约：每条结论给「**位置 + 片段 + 来源类型**」

---

## 8. 切换协议

```
开工/换 req：读 CARD → 取 分支/工作区 → work_dir 指过去（触发换代）→ recall 该 req 的 topic → 干活
收尾：       结论落项目仓文档 → 更新 CARD 状态 → 经验写 topic / 经验索引（只追加）
```

## 9. 变更策略（本文件的另一半）

### 9.1 新建 Bot

| 情形 | 做法 |
| --- | --- |
| req 立项 | 建一个 req Bot：命名 `<项目>-<编号>`，`bot.workDir` 指该 req 的工程根 |
| 横向职能长期存在 | 建共享 Bot：常驻"家"，不挂任何 req 域 |
| 一次性事务 | **不建 Bot**，派 subagent |

**并发护栏**：同时活跃 req ≤ 4；超限就先收尾再开新 req，不靠加人解决。

### 9.2 修改 Bot（按代价从大到小）

| 改动 | 代价 | 规则 |
| --- | --- | --- |
| **改 instructions** | 最大：该 Bot 的提示词前缀缓存**整体失效** | 只在职责/边界真变了才改；**身份段措辞保持字节稳定**（这是缓存能命中的前提）；改完跑一次最小任务确认 |
| **改 `work_dir`** | 触发**换代**（上下文重置，写交接笔记，保留最近约 16k） | **换 req 才改**；不把它当"上下文开关"频繁切 |
| **改模型** | 需要目标路由有凭据 | 改前先确认该路由有可用凭据（无 key 的路由不可用）；**换模型须先经用户同意**；一次只改一个 Bot |
| **改名/角色标签/颜色** | 无 | 随时可改 |
| **改记忆** | 无 | 用户要求记住的才写；一条一个事实；事实变更是 replace 而不是叠加 |

### 9.3 停用 Bot

- **req 完成或废弃 → 立即停用**（插件会归档其记忆）
- 停用前：结论落项目仓文档 + 更新 CARD 状态 + 经验入 topic/经验索引
- 共享 Bot 只在职能消失时停用

### 9.4 谁有权改

- **用户**：技术方案、策略条款、指标、架构方向——一律由用户拍板
- **Chief（Main Bot）**：会话管理与成员 Bot 管理——建/改/停 Bot、模型分配、建群、工作区授权、跨 req 冲突裁决
- **任何 Bot**：可改自己（非 Main Bot），但同样受本节规则约束

### 9.5 留痕与回执

- 策略本身的变更：提交到本仓库（**公开仓库 → 提交前脱敏**：机器路径、用户名、内部代号一律不出现）
- 每次建/改/停 Bot：向用户一行回执（做了什么、为什么、影响面）

---

## 10. 明确不做

- ❌ 不发明组织结构（岗位体系、汇报线、治理规范）
- ❌ 不为每个任务建人、建群
- ❌ 不在 req 目录另存记忆正文
- ❌ 不整读索引/大文件（探测优先）
- ❌ 不自行拍板技术方案（只汇总、只执行）
