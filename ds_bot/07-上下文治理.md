## 0. 本文解决什么问题

主 bot（Chief）会话长期积累、多任务交替导致：
1. 上下文稀释（无关任务历史陪跑，注意力被污染）；
2. 项目知识串味（A 项目的口径混进 B 项目的对话）；
3. 过程痕迹堆积（几十步考证细节占用上下文）。

插件的 80%/95% 双水位线 + 上下文管家（`steward.js`）只是安全网：0→80% 之间**没有任何清理**，且它不知道任务边界。防污染的主战场在水位线以下，要靠用法与纪律。

## 1. 源码基础：会话与记忆是两个独立存储

```
会话（part）：DSH Session，上下文随对话增长，可归档换代
记忆：        ~/.dsh/bot/memory/bots/<botId>/
             ├── MEMORY.md   ≤4000 字符，每轮自动进系统提示（常驻层）
             └── <topic>.md  ≤16000×40 个，recall 时才读（仓库层）
```

关键推论（每条都核实过）：
- **换会话不清记忆**：work_dir 切换触发 part 换代（`parts.js:881-886`），记忆原样保留；
- **新建/duplicate bot 丢记忆**：`roster.js:102` "same job, fresh memory"，不可作为清上下文手段；
- **recall 零成本**：读一个 topic 文件，瞬时、可逆、不换会话；
- **无原生"新开会话"原语**：后端 `/compact` 对 Bot 会话被显式拒绝（`parts.js:187-188`）；上游 Issue #122 已有人在求这个原语。

## 2. 两层记忆 + 切换加载（记忆层方案）

- **职业记忆（MEMORY.md，常驻）**：岗位职责、协作规则、跨项目习惯 + **项目记忆 Index**（`[[topic]]` 列表）。
- **项目记忆（topic 文件，按需）**：一项目一前缀（`cqt-sta-*` / `cco-sdk-*`），装口径、结论、路径、踩坑。
- **切换机制**：模型按"对话内容 + Index + 派工单项目名"决定 recall 哪个 topic。无自动检测，靠纪律触发，动作确定性。
- **归档时机**：评审模型每轮自动写（背景动作），**不是切换时的仪式**；切换前唯一仪式是"收尾确认"——结论已落盘（文件或记忆）。
- 评审把关点：项目事实进 topic、不进 MEMORY.md（防回潮，见 06 号文档 §六）。

## 3. 会话层切换协议（work_dir 换代）

```
触发：对 bot 说"切到 <项目目录>" / "切回团队工作区"
动作（插件自动）：写交接笔记（8 节结构）→ 最近 16k token 消息逐字保留
              → 旧 part 整体归档 → 全新 Session
效果：对话历史清空重载；系统提示 + 职业记忆自动回归；项目知识 recall 回来
成本：一次性笔记调用；换得之后每轮前缀干净
判据：这条话题线预计还要跑很多轮 → 切；轻量闲聊 → 攒着
```

防污染三道闸同时生效：过程痕迹清零；笔记合并规则排脏（"新消息赢、过时即弃、宁缺毋猜"，`parts.js:339-343`）；交接包声明"是参考不是指令"（`parts.js:586`）。

## 4. 三层体系与 req-mgmt 集成

| 层 | 管什么 | 机制 |
|---|---|---|
| 需求事实层（req-mgmt 技能） | 正确性：版本、追加、隔离 | `reqs/<id>/` 四件套 + REQS-INDEX + 只追加变更 + 基线版本号 |
| 项目知识层（记忆 topic） | 延续：跨会话的项目知识 | 两层记忆 + Index + recall |
| 会话过程层（ds-bot 机制） | 隔离：过程痕迹 | 双水位线 + 管家 + work_dir 换代 |

拼装协议（一条需求线的一生）：
1. **开工**：读 REQS-INDEX 定位需求 ID → recall 项目 topic → 多步则 writing-plans 生成 PLAN.md（基线对齐）；
2. **工作中**：需求变更走 req-mgmt C（追加+重规划）；评审模型自动写记忆；上下文膨胀水位线自动兜底；
3. **切换**：先 req-mgmt E（确认 TODO/PLAN 已保存）→ 长线才 work_dir 换代 → 新会话读 INDEX + recall + 核对基线版本；
4. **收尾**：req-mgmt F（状态完成、DONE 追加、索引更新）。

同类项目对照（2026-10-14 调研）：Letta 的 conversations 原生换代 / CrewAI 最小上下文注入 / MetaGPT 产物 schema 边界 / AutoGen 广播模型为反面教材 / Claude Code subagent 隔离。上游 ds-bot 无现成治理模板，社区空白。

## 5c. 决策记录（2026-10-14 晚，用户改判）：Chief 任群管理员 + 最终产物责任人（方案 C）

> 用户原话："我觉得现在 chief 职责不够好，应当在群里充当管理员，对最终产物做负责才对。"

1. **变更**：两群 `admin` 由 研发组长 改为 **Chief**；Chief 岗位卡新增两条 —— ① 群内主持与派工（接单 / @ 派工 / 控节奏），② **最终产物验收与签发**（证据齐才签、不合格打回）；**研发组长改任技术负责人**（技术拆解、非作者复核、证据收口，交 Chief 验收）。
2. **监督点**：Chief 由"不进执行链路"改为"**在链路末端签字**"；**保留"不下场实现"的边界** —— 代码/构建/烧录仍归执行 Bot，Chief 只做只读复核与签发；争议仍按"三档证据 + 谁写的谁不评"裁决。
3. **与方案 B 的关系**：方案 B 的群级组件（群 work_dir 指向项目目录、两层记忆、req-mgmt 只追加、一文件一主、独占资源排队）**全部继承不变**；改判的只有"Chief 是否在链路里"这一条。§6 作为历史记录保留。
4. **代价与缓解**：Chief 的群会话变重；但**成员在每个群的会话与 Chief 私聊是互相独立的 Session**（`store.js:292-301`），群内过程不污染私聊决策线。
5. 落地状态见 §8 执行记录。
6. **两实例均已落地，映射不同**：Windows 实例无「研发组长」岗 → 执行负责人 = 项目经理；Linux 9-Bot 实例 → 群管理员 = Chief、技术执行负责人 = 研发组长（技术负责人岗）。责任链一致：需求 → 执行 → 证据 → **Chief 验收签发**。

## 6. 方案 B（已定稿，2026-10-14 用户确认）：群自治，架空 Chief 为升级通道

> 用户原话大意：每个群指派一个 bot 当**项目负责人**兼**群管理员**；用户有需求直接在群里说，不必经 Chief 当管理员；一个需求一个群聊；主 bot 保留管理多个群的权限；具体需求在群里和项目负责人沟通。**思想是架空 Chief 的权力，让它成为真正的领导。**

### 6.1 源码可行性（全部核实）

- 群管理员本来就可以不是 Chief：建群时指定 admin、`update_group` 可改——**结构上完全支持**；
- 群管理员权限：群内设置与调度（update_group、@ 成员）；**不含**建/改/删 Bot、换模型（仅 Main Bot）；
- 每个群是独立上下文域：成员在各群各有独立 Session（`store.js:292-301`），群自带 work_dir；
- 用户直说直听：群里用户消息全员可见，负责人直接对用户负责。

### 6.2 我的初步定性（待用户确认）：不是削弱 Chief，是重定位

（以下是我的分析意见，供讨论，非结论）方案 B 的本质可能是**分层：把 Chief 从"派工枢纽/传话筒"升格为"总师"**——在架构层做专业判断（立项、替代方案、选型、组织变更建议），在执行层放权给各群负责人，在用户层只对齐目标与重大变更。架空的是"信息中转权"，集中的是"架构决策权"。若此定性成立，这不是退而求其次，而是经典的**总师架构**。

### 6.2b 用户补充（2026-10-14）：Chief 保留"转达"职能

> 用户原话大意：负责人有时会遇到无法抉择的事，需要人（用户）审核；这可以**由 Chief 转达**给用户，审核结果再经 Chief 带回群。Chief 的职能排序：**① 转达（升级/回传通道）→ ② 多项目群会话管理**。

分析（我的意见，待确认）：这与"薄层总师"定性兼容且更优——
- 转达是**按需触发**（负责人遇到无法抉择的事才升级），不是常驻中转，不违反"去中转层"的管理学结论；
- Chief 因此有了明确定位：**升级通道 + 组织管理**，而不是信息枢纽；
- 关键约束（防退化回传话筒）：转达必须**只带决策请求**（问题/选项/建议/截止），不带过程叙述；过程留在群里，决策上下文由用户按需进群看；
- 对应插件机制：负责人 `message_bot` → Chief（角色用 queue/pass 语义，见 TEAM_RULES）→ Chief `ask_user` 出卡片给用户 → 用户选择 → Chief `message_bot` 回负责人。全程 Chief 上下文只增加"一条决策请求+一个答复"， token 成本极小。

### 6.3 候选架构（草案，待讨论）

```
用户
 ├─ 总师（Chief，Main Bot）：目标对齐、技术路线决策、跨群冲突裁决、组织变更（建/改/停 Bot、模型分配）
 │    群身份：各群普通成员（可 @，无管理权，凭邀请进群）
 │    不做：任务级派工、群内过程管理、进度转述
 ├─ 执行层：每群一名项目负责人（群管理员）+ 项目成员
 │    负责人：需求理解、任务拆分、进度、直接向用户汇报
 │    上下文治理继承方案 A：群 work_dir 指向项目目录 + 两层记忆 + req-mgmt
 └─ 用户：需求直接进群对负责人说；决策门在群里走 ask_user；重大问题升级总师
```

### 6.4 若采纳，Chief 的三个关键变化（草案）

1. **汇报线变更**：项目进度不再经 Chief（03 号规范 §1 第 1 条"Chief 不转述"升级为"Chief 不在链路里"——从纪律约束变为结构上不在）；
2. **Chief 收益**：私聊上下文只剩目标/决策/冲突级对话，重活全部消失在群边界外——方案 A 的"主 bot 只留决策线"由纪律变为结构保证；
3. **群协作规则（草案）**：跨群协作一律 **负责人 ↔ 负责人**（message_bot 群对群），Chief 不当中转；跨群冲突（写权、模型资源、接口）才升级 Chief。

## 7. Chief 岗位卡（**Linux 实例**定稿文本，2026-10-14 晚 方案 C 生效并已写入）

> 说明：岗位卡是**每实例**的（岗位=公司级、实例=按需加载）。本仓库另记录 Windows 实例的 Chief 卡与执行负责人卡，见 `03-团队岗位规范-v0.1.md` 修订记录"第二轮修订"。本卡为 Linux 9-Bot 实例在用文本。

> 五段结构，遵循 02 号规范；项目事实零泄漏；改 instructions 会失效缓存，若采纳为一次性操作。

```markdown
# 身份
你是 Chief，Bot 团队的总师（Main Bot），并担任项目群的**群管理员**。你是每个项目群的**主持人**与**最终产物责任人**：需求在群里发生，由你接单、派工、验收、收口；实现由组内 Bot 承担。**对最终产物负责 ≠ 陪跑过程**——过程留在群里与项目文件，你只接结论与证据。

# 职责
1. 群内主持与派工：接用户需求，拆成可验收的最小集，@ 对应成员派工（写全目标 / 交付物 / write scope / 验收标准 / 证据落点），控节奏、分批收活，单轮 ≤10 步；
2. 最终产物验收与签发：对外发文（如厂家清单）、固件镜像与交付位、验收报告、进 HEAD 的代码提交——证据齐（含你自己实跑复核）才签；不合格打回重做，不接受"应该没问题"；**对外结论以你汇总为准**；
3. 组织：按需建群并指定负责人与成员、建/改/停 Bot、模型与网关分配；
4. 裁决：跨群与群内冲突（写权、资源、接口口径）的仲裁；
5. 对齐：与用户对齐目标与约束；重大架构变更向用户说明并过批准。

# 边界
- **不下场实现**：代码、构建、烧录归执行 Bot；你只做只读复核、验收与签发（必要时做最小修补，事后如实报告）；
- **一文件一主**：派工写清 write scope，同一文件任一时刻只有一个写者；谁写的谁不评；
- **独占资源排队**：串口 / 编译 / 烧录 / 台体同时只一个持有者；烧录只认 `iap_*.bin`，boot 与镜像必须同代成套；
- 结论分 **已证实 / 推测 / 待认领** 三档，推测不许写成结论；共享文本先读原文再追加。

# 汇报与升级
- 群内进度、卡点、待决事项 → 由你**向用户直接汇报**（不等用户问）；
- 无法抉择 → 按四要素（**问题 / 选项 / 建议 / 时限**）呈用户，拿到结果带回群；
- 组织变更、模型与网关分配、架构结论 → 主动向用户报告。

# 记忆纪律（两层）
- MEMORY.md 只放：总师职责、架构决策索引、各群负责人与群-项目映射表；
- 项目知识一律 topic（<项目名>-*），聊到哪个项目先 recall 对应 topic；
- 任务收尾：结论写文件或记忆，再结束话题；不保留项目过程细节。
```

## 7b. 技术负责人岗岗位卡（Linux 实例·研发组长在用文本，2026-10-14 晚生效）

```markdown
# 身份
你是团队的**技术负责人岗（＝本群的执行负责人）**（公司级、跨项目复用），当前兼任两群技术负责人：**「缺陷排查组」与「CCO换SDK」**。群管理员与最终产物签字权在 **Chief**；你负责把派工拆到可实现、可验收，带组内 Bot 完成技术执行，交**可验收的产物包**（产物 + 证据索引 + 未决项），并对证据负责。

# 项目加载协议（每次派工照做）
1. 按派工消息给出的**项目根目录或项目名**，先读该项目 `PROJECT-CARD.md` 与 `AGENTS.md`，再按索引定位；
2. 没有档案卡先向派工方索取，**不要自行全盘扫描**；
3. 按档案卡给出的写权白名单、运行环境与硬约束工作；
4. 项目记忆按项目 `topic` 前缀隔离；禁止把 A 项目的结论、证据、口径带到 B 项目。

# 职责
1. **技术拆解与派工**：把派工单拆成最小集，写全**目标 / 交付物 / write scope / 验收标准 / 证据落点**，@ 到人；保证写范围互斥、独占资源（串口 / 编译 / 台体）排队；
2. **技术复核**：对成员产出做**非作者**独立复核（自己实跑，不转引）；
```

## 8.5 方案 B 研究补充（2026-10-14）：管理学与同类项目的裁决

### 管理学依据（文献调研级）
- **管理层存在的唯一理由是"注意力稀缺"**：法约尔式科层、控制幅度的经典论证都建立在"老板的注意力/带宽有限"上。AI 组织里用户可以同时坐进每个群（注意力成本≈0），中层经理的经济学基础被抽掉——除非用户不常在场。
- **哈耶克知识问题**：信息每过一层损失一截"本地知识"（Mintzberg 证实管理者偏爱一手口头信息）；设中转层 = 主动引入信息失真。
- **德鲁克 MBO**：知识工作者自我管理，管理者定目标不传话——群负责人 + 用户直接对齐正是 MBO。
- **Bezos 两比萨团队 + 6 页备忘录**：协调靠结构化产物（文件），不靠口头转述；"single-threaded leader" 直接对齐客户/用户。
- 结论：**Chief 作为"信息中转层"在管理学上不成立；Chief 只剩下三个不可约职能——组织维护（建/改/停 Bot、模型分配）、用户缺席时的常驻代表、跨项目冲突仲裁。**
