# 嵌入式功能说明文档标准

## 概述

以《分钟采集功能说明-RD20260803.md》为标杆，写嵌入式功能说明时遵循固定写作标准。核心原则：**结构分层 + 信息密度 + 表格图形化 + 诚实披露 + 落地可操作**。让文档从「是什么」一路走到「怎么用、怎么测、怎么排障」。

**参考范本：** `cco/doc/分钟采集功能说明-RD20260803.md`（写作时对照其语气与密度）。

## 写作标准

1. **文件与头部**：文件名 `功能名-RDYYYYMMDD.md`；开头引用块写明 状态 / 版本 / 日期 / 读者 四项。
2. **先讲机制再落细节**：概述用 2–4 段自然语言讲清核心机制，再配**具体时间/数值窗口示例**（如「5 分钟任务在 HH:09:00–HH:09:59 补抄 HH:00:00」），让规则可验证。
3. **场景化分节**：核心场景各成 `###` 小节，编号步骤化描述。
4. **表格优先于散文**：接口、参数、存储、测试等结构化信息一律用四列表格，只有机制性叙述用段落。
5. **图形用 mermaid**：业务流程、状态机、数据流用 `flowchart TD`/`flowchart LR`，含判断菱形；异常流程单列图。
6. **完整覆盖异常**：异常分支表覆盖构造失败、超时、离线、缺档案、重复上报、stale ACK 等所有失败路径。
7. **诚实披露**：必写「已知局限」与「实现与需求不一致说明」，主动暴露妥协与未验证项。
8. **落地可操作**：依赖模块写源码路径；运维观测给串口命令、日志关键字、排查步骤；测试场景给具体时标；末尾用一小段「简短摘要」收尾便于转述。

## 排版

遵循 `chinese-documentation` 规范：中英文/数字间加空格、中文语境全角标点。

## 常见错误

- 机制讲不清直接上字段/代码 → 概述先用自然语言讲透机制
- 规则无具体例子 → 必须配时间/数值窗口示例
- 只写正常流程 → 补异常图 + 状态机表 + 异常分支表
- 结构化信息用散文罗列 → 改四列表格
- 掩盖局限与差异 → 写已知局限、实现与需求不一致两节
- 无排查手段 → 加运维观测（命令、日志关键字、排查步骤）

## 检查清单

- [ ] 文件名 `功能名-RDYYYYMMDD.md`，头部有 状态/版本/日期/读者
- [ ] 概述讲清机制并给出具体时间/数值示例
- [ ] 场景分节步骤化；结构化信息用表格
- [ ] 有 mermaid 正常流程、异常流程、数据流图 + 状态机表 + 异常分支表
- [ ] 有已知局限、实现与需求不一致、运维观测
- [ ] 末尾有简短摘要；排版符合 chinese-documentation
