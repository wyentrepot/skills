# 工作台使用不便记录（踩坑清单）

> 记录 AI/用户实际使用工作台时遇到的"不好用、乱打转、浪费 token"现象，每条给出现象、根因、正确姿势与改进建议。
> 便于后续修订启动脚本 / skill 文档 / run.py，避免重复踩坑。持续追加。

## 1. 启动命令与仓库布局不符：`ModuleNotFoundError: No module named 'shared'`

- **日期**：2026-09-18（安徽营销双模搜表问题排查会话）
- **现象**：按 skill 文档 `cd <WORKBENCH_ROOT>/apps && PYTHONPATH=apps:libs python -m workbench.run` 启动，直接报
  `ModuleNotFoundError: No module named 'shared'`，白费一次启动。
- **根因**：本仓库 `shared` 包在 `libs/` 下（`/01-workfile-ai/01-zzt/ZZT_SELF/libs/shared`），不在 `apps/` 下；
  `PYTHONPATH=apps:libs` 是**相对 cwd 解析**的，从 `apps/` 目录起跑时 `apps` 子路径根本不存在 → `apps` 没进 sys.path。
- **正确姿势**：从**仓库根**起跑：
  ```bash
  cd /01-workfile-ai/01-zzt/ZZT_SELF && PYTHONPATH=apps:libs python3 -m workbench.run
  ```
- **建议**：① 修订 ai-control-plane skill 的启动说明（改为仓库根起跑或给绝对路径）；② run.py 顶部加 sys.path 兜底（把仓库根与 libs 拼进 path），彻底消除 cwd 敏感。

## 2. v2 免 token 需要显式 `WORKBENCH_LOCAL_FULL_ACCESS=1`，漏掉即 401

- **日期**：2026-09-18
- **现象**：第一次启动未带该环境变量，`GET /api/ai/v2/capabilities` 返回 401「缺少 Bearer token」，AI 以为要去找人拿 token，绕路。
- **根因**：skill 写明"本机启用 WORKBENCH_LOCAL_FULL_ACCESS=1 且对端为 loopback 才免 token"，但启动命令示例里没带，容易漏。
- **正确姿势**：启动时一并带上：
  ```bash
  cd /01-workfile-ai/01-zzt/ZZT_SELF && WORKBENCH_LOCAL_FULL_ACCESS=1 PYTHONPATH=apps:libs nohup python3 -m workbench.run > /tmp/wb.log 2>&1 &
  ```
- **建议**：loopback 来源默认视为 local_full，或启动横幅/health 接口提示"当前 v2 需 token，环境变量未开"。

## 3. `pkill -f workbench.run` 误杀自身 shell（连续两轮 SIGTERM，最典型的"乱打转"）

- **日期**：2026-09-18
- **现象**：想重启工作台，执行 `pkill -f "workbench.run"`，结果整条命令被 SIGTERM 打断——连续两轮。第二轮即使给模式加了 `[w]orkbench.run` 括号技巧，同一条命令行里 `pgrep -af "workbench.run"` 参数仍含明文串，pkill 正则照样匹配到自己这条 bash -c 的命令行。
- **根因**：`pkill/pgrep -f` 匹配的是**完整命令行**，而 bash -c 的命令行包含命令文本本身；只要同一条命令里任何位置出现能被模式命中的明文，就会自杀。
- **正确姿势**（任选其一）：
  ```bash
  # ① 先 pgrep 拿 PID 再 kill（模式加括号技巧，且整条命令不得再出现明文）
  pid=$(pgrep -f "[w]orkbench.run"); [ -n "$pid" ] && kill $pid
  # ② 更稳：直接调工作台自带 stop 接口，不碰进程
  ```
- **建议**：run.py 支持 PID 文件（如 `/tmp/workbench.pid`）+ `--stop` 参数；skill 补一条"停工作台别用 pkill -f"的红线。

## 4. headless 环境启动噪音：`xdg-open: w3m: not found`

- **日期**：2026-09-18
- **现象**：工作台启动成功后自动尝试打开浏览器，WSL 无图形环境报 `xdg-open: no method available for opening 'http://127.0.0.1:8790/'`、`w3m: not found`。
- **影响**：无害但污染启动日志，AI/用户容易误判"启动失败"，多查一轮。
- **建议**：检测到无 DISPLAY / headless 时跳过 open，或加 `--no-open` 参数、环境变量开关。

## 5. 外部日志进索引入口藏在源码里，skill 文档未记载（先误判要拷文件）

- **日期**：2026-09-18；2026-09-20 核查修订（入口路径当时写错，已更正）
- **现象**：测试问题附带日志（`/01-issuse/安徽营销双模/ZTTLOG.txt`）在问题目录里；skill 的 listener.md 只记载了 `data/logs/侦听台/` 目录与 v1 `listener/ensure` 等接口，没有提"索引任意路径日志"的入口。AI 先入为主以为必须手工拷贝进 `data/logs/侦听台/`，来回探索（多次 grep app.py）才找到：
  **（当时误记为 `POST /api/logs/open`——那是 listener 子应用内部路径，仅直连 8765 独立版可用；
  经 8790 workbench 网关实测 404，正确入口见下【正确姿势】。）**
- **正确姿势（2026-09-20 修订）**：`POST /api/listener/logs/open`，body `{"path": "<绝对路径>"}`（202），
  即可对任意可读日志文件建立索引（路由本体 `apps/listener/app.py:273` → `log_service.start_index`，
  挂载剥前缀规则见 api-contract.md §1.2）；随后 `GET /api/listener/logs/status` 轮询、
  `/api/listener/indexes/{id}/frames` 查帧；串口采集中会 409，先停采集。
- **文档真实状态（2026-09-20 核查）**：`features.md:20` 一直记载着正确链路（logs/open 202 → status 轮询，
  与串口采集互斥 409）；`api-contract.md:91` 记的是内部裸路径——真正的坑是两处口径不一致，
  而非完全没有记载；listener.md 任务文档确实未提该入口。
- **影响**：入口存在但文档缺口，每次离线排查都要重新翻源码找接口，token 浪费在"找入口"而不是"查数据"。
- **建议**：✅ api-contract.md §3.2 已补网关路径与告警注记（2026-09-20 核查）；⬜ listener.md 补一节"离线日志索引"（logs/open + logs/status + indexes/frames 链路）。
