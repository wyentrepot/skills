# req-mgmt — 需求/进度管理 playbook

> 适用：公司项目分支多、临时小需求与大需求并存、AI 开发时需求频繁变更后混乱的场景。
> 本 playbook 只描述**流程与交互规范**（遵循 DECISIONS.md #8「跨会话知识分离」），不含领域常量。

## 核心理念

1. **决策/需求只追加、不覆盖**（ADR 模式，源自 AGENTS.md）：需求基线只存当前生效版本；每次变更追加一条记录，禁止静默覆盖。防止需求前后矛盾、AI 基于旧版本写代码。
2. **多需求切分 + 上下文隔离**：同一项目多个需求并存时，每个需求独立目录，互相不污染，可灵活切换。

## 目录结构（项目内嵌）

```
reqs/
  0001-<需求slug>/          # 每个需求一个目录（ID 自增，slug 用英文短横线）
    REQS.md               # 该需求基线（只存当前生效版本）+ 变更记录（只追加）
    TODO.md               # 该需求的任务清单（阶段化）
    DONE.md               # 该需求的完成日志（只追加，最新在上）
REQS-INDEX.md             # 项目级索引：所有需求 + 状态 + 所属分支
```

> 每个需求对应一个 git 分支；切分支即切需求。需求文件随分支走。

## 核心流程

### A. 会话开始（定位需求）
1. 读 `REQS-INDEX.md`，确认当前 git 分支对应哪个需求。
2. 若当前分支无对应需求 → 是"临时小需求"还是"新大需求"？按需新建 `reqs/<id>/` 并在索引登记。
3. **只加载当前需求的上下文**（该需求目录下的文件），不把其他需求历史灌进来。

### B. 开发前对齐（关键防混乱步骤）
1. 读当前需求的 `REQS.md`，核对**当前生效基线版本**（看最新变更记录）。
2. 若用户口头需求与基线不一致 → 先走「C. 需求变更」，再开发。
3. 确认基线后才开始写代码。**绝不在未核对基线的情况下动工。**

### C. 需求变更（只追加，不覆盖）
1. 在 `REQS.md` 的变更记录区末尾**追加**一条：
   ```
   ### 变更 N ｜ YYYY-MM-DD ｜ 变更人
   - **改成什么**: <一句话>
   - **为什么**: <原因>
   - **影响**: <涉及文件/分支/其他需求>
   - **被取代**: 变更 N-1（若覆盖上一版）
   ```
2. 更新顶部基线为最新版本，**正文旧内容保留在记录区**。
3. 若影响其他需求，在该需求记录区追加交叉引用说明。

### D. 任务与进度
- `TODO.md`：阶段化（`## 阶段` + `- [ ] 任务`）。大需求按里程碑分阶段，临时小需求单阶段即可。
- 完成一项勾掉 `- [x]`；全部完成则移到 `DONE.md`（追加，最新在上）。

### E. 多需求切换
1. 切 git 分支前，先确认当前需求的 `TODO.md` 已保存进度（未完成的任务原样保留）。
2. `git checkout <另一需求分支>` → 回到「A. 会话开始」重新定位。
3. 切换只换上下文，双方进度独立保存，随时切回。

### F. 完成
- 需求完成 → 在 `REQS-INDEX.md` 把该需求状态改为「✅ 已完成」，`DONE.md` 归档。

## 交互规范
- AI 动工前必须执行 B（核对基线）；未核对就写代码属违规。
- 需求变更必须追加记录，禁止静默改写基线正文。
- 每次会话结束前，若有进度变化则更新 `TODO.md` / `DONE.md` / `REQS-INDEX.md`。
- 模板见 `templates/` 目录。

## 辩解表（AI 绕过流程的借口 → 现实）

> 违反字面即违反精神：以下借口都是绕开流程的合理化，一律不成立。

| AI 的借口 | 现实 |
|----------|------|
| 「这个变更很小，不用走变更记录吧？」 | 与大小无关，任何基线变更都必须追加记录；小变更最容易被后续忽略，更要留痕。 |
| 「REQS.md 我看过一遍了，基线没变，直接写」 | 核对基线是动工前动作，不是凭记忆；用户口头需求与基线不一致时必须先走流程 C。 |
| 「先写代码，回头补记录」 | 回头补 = 大概率不补；先追加变更记录再动工，顺序不可颠倒。 |
| 「旧需求本来就这么写的，沿用就行」 | 旧需求可能是已被取代的旧版本；只看最新变更记录所定的**当前生效基线**。 |
| 「这需求不在 REQS-INDEX 里，直接做吧」 | 不在索引 = 未登记；先建目录并登记（流程 A），否则进度无处保存。 |

## Red Flags（动工前自检，任一命中即 STOP）

- [ ] 我核对了 REQS.md 的**当前生效基线**（不是记忆中的版本）？
- [ ] 用户口头需求与基线不一致时，我走了流程 C 追加变更记录？
- [ ] 该需求已在 REQS-INDEX.md 登记、目录已建？
- [ ] 切分支前，当前需求的 TODO.md 进度已保存？
- [ ] 我正要静默改写基线正文或删除历史变更记录？
