## 逐条记录

### #1 需求变更采用 ADR 式只追加，禁止静默覆盖
- **日期**: 2026-02-19
- **状态**: ✅ 生效
- **决定**: 需求基线（REQS.md）只存当前生效版本；任何需求变更都必须在其变更记录（CHANGES.md）末尾追加一条记录（谁/何时/改成什么/为什么/影响），禁止静默覆盖原需求；被取代的基线内容只在变更记录里标注状态，正文保留。
- **理由**: 需求频繁变更导致项目混乱的根因是"需求被静默覆盖、前后矛盾、AI 基于旧版本写代码"。只追加模式让每条变更可追溯、可回滚，AI 动工前可核对当前基线版本。
- **影响**: 每次开发前多一步"核对当前基线版本"；变更时多一步追加记录；换取需求历史完整、可回溯、不漂移。
- **被取代**: 无

### #2 同一项目多需求并存：按需求切分 + 上下文隔离 + git 分支对齐
- **日期**: 2026-02-19
- **状态**: ✅ 生效
- **决定**: 同一项目内不再维护"单一当前需求"。每个需求一份独立目录（`reqs/<id>/`），内含该需求专属的 REQS.md / CHANGES.md / TODO.md / DONE.md；项目级 `REQS-INDEX.md` 统一索引所有需求（ID、标题、类型、状态、所属分支）。会话开始时先读索引定位"本次做哪个需求"，只加载该需求上下文，切换需求 = 换上下文，各方进度独立保存、互不污染。每个需求对应一个 git 分支，切分支即切需求。
- **理由**: 公司项目临时小需求与大需求并存、分支多，若用单一需求文件，插入其他需求会互相污染、进度丢失，回到混乱。
- **影响**: 目录结构多一层 `reqs/<id>/`；切换需求前需先读索引确认当前分支与需求对应；换取多需求并行时灵活切换、进度不丢。
- **被取代**: 无

### #3 变更记录内嵌于 REQS.md，不再单设 CHANGES.md 文件
- **日期**: 2026-02-19
- **状态**: ✅ 生效
- **决定**: 需求的变更记录内嵌在 `REQS.md` 底部「变更记录」区（顶部只存当前生效基线，历史变更追加在下方），不再单独维护 `CHANGES.md` 文件。每个需求目录为三件套：REQS.md / TODO.md / DONE.md。
- **理由**: 变更记录与基线同处一个文件，阅读与维护更简单；实现（技能与模板）实际已采用内嵌方式，此决策将命名与落地对齐，避免决策（CHANGES.md）与实现（内嵌 REQS.md）脱节。
- **影响**: 需求目录从四件套（REQS/CHANGES/TODO/DONE）简化为三件套（REQS/TODO/DONE）；决策 #1/#2 正文中「变更记录（CHANGES.md）」的表述按本决策解释为 REQS.md 底部变更记录区，正文不改（遵循只追加不覆盖铁律）。
- **被取代**: 无

### #4 DECISIONS.md 设上限：满 10 条归档重启，生效决策重新登记
- **日期**: 2026-02-19
- **状态**: ✅ 生效
- **决定**: 为 DECISIONS.md 增加**上限**：正文全部 ADR 记录（`### #N` 条目，**含已被取代的**）累计达到 **10 条**时，触发「归档重启」：① 把当前 DECISIONS.md 整份移入 `archives/`（含日期命名，如 `archives/DECISIONS-YYYYMMDD-HHmm.md`）；② 新建一份从零开始的 DECISIONS.md；③ 新文件按原 #1、#2、#3… 的顺序**重新登记当前仍生效的决策**作为初始基线（仍保留逐条记录正文、编号从 1 重新起）；④ 若原 #4 本身上限规则仍在生效期，它也在重新登记之列。`SKILL.md` 的 DECISIONS.md 相关规则随技能内容走，归档重启不影响 SKILL.md 本身。
- **理由**: 之前的 ADR 规则「只追加、永不删除」没有上限，长期积累后 DECISIONS.md 越长越长、堆积过多，违背该文件「聚焦当前生效决策」的初衷，阅读与加载成本上升。设 10 条上限既保留"全量历史永远可回溯"（归档不删除），又强制定期收敛回到"仅当前生效决策 + 精简正文"的初始状态。
- **影响**: 需要配套归档动作（脚本 `scripts/archive.js`，或手动按 SKILL.md 流程 G 操作）；DECISIONS.md 以归档+重启为唯一合法瘦身方式，**任何时候都禁止直接删减正文**；被取代的旧记录在归档里永久保留，不算丢失。
- **被取代**: 无（本决策生效后，原「只追加、永不删除」表述按本决策解释为"在当前 DECISIONS.md 生命周期内只追加；满 10 条通过归档重启瘦身"，正文不改。）

### #5 归档重启采用「3 条缓存 + 7 条新增」滑动窗口，防止技能失忆
- **日期**: 2026-02-19
- **状态**: ✅ 生效
- **决定**: 取代 #4 中「仍生效决策重新登记」的执行方式。DECISIONS.md 累计满 **10 条**（含已被取代的）归档重启时，**新文件不再从零开始**，而是**复制当前文件的最后 3 条记录（#8、#9、#10）作为缓存种子**，依次重排为新文件的 **#1、#2、#3**（标题、日期、状态、正文原样保留）；随后新增的决策从 **#4** 开始编号。新文件每个生命周期实际容纳「3 条缓存 + 最多 7 条新增」，再次满 10 条（新增到 #10）即再次归档。归档文件仍完整保留全量历史（`archives/DECISIONS-YYYYMMDD-HHmm.md`），不删除。
- **理由**: #4 的「重新登记仍生效决策」在旧决策被取代较多时，新文件可能只剩一两条，甚至为空，技能在会话重启后丢失了最近的决策上下文（失忆/失效）。改为保留**最近 3 条**作为缓存，新文件永远带着最近 3 条决策开场，AI 一读就有连续上下文；同时每个生命周期只新增 7 条，窗口短、防堆积、始终可追溯。
- **影响**: 归档脚本（`scripts/archive.js`）的生成逻辑从"筛选仍生效"改为"取末尾 3 条重排为 #1–#3"，SKILL.md 流程 G 同步改写；文件始终为 10 条或以内；#1–#3 为缓存种子、#4 起为新增，编号含义变为"本生命周期内的记录号"而非全局历史编号。
- **被取代**: #4 的重新登记方式（#4 其余部分：满 10 触发、归档进 archives/、禁止删减正文，继续生效）。

### #6 多需求上下文与 Git 分支解耦，分支仅作记录
- **日期**: 2026-09-02
- **状态**: ✅ 生效
- **决定**: 需求目录、基线与进度按需求 ID 独立管理；Git 分支只记录关联代码分支，不作为需求选择器，不要求随需求上下文切换。
- **理由**: 需求上下文应保持稳定并可独立切换，避免项目分支切换把需求记录和会话上下文绑定在一起；人工可以按实际开发需要自行决定是否切分支。
- **影响**: `REQS-INDEX.md` 的分支列改为“关联代码分支（仅记录）”；流程 A/E 不再自动执行 `git checkout` / `git switch`，多需求目录隔离与 TODO 进度保存规则继续生效。
- **被取代**: #2 中“每个需求对应一个 git 分支，切分支即切需求”的执行方式；#2 的多需求独立目录与上下文隔离继续生效。
