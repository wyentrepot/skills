# examples — 需求/进度管理示例

> 演示 req-mgmt 如何解决「需求频繁变更导致混乱」+「多需求灵活切换」。
> 场景：协议开发，初始需求中途变更，又插入一个临时小需求，最后切回原需求。

## 场景时间线

### 1. 初始需求（0001-协议A字段扩展）
- `REQS.md` 基线 v1：给协议 A 增加字段 X。
- 会话开始，AI 读 `REQS-INDEX.md` 定位 → 读 `REQS.md` v1 → 确认做字段 X 解析。

### 2. 需求中途变更（核心防混乱步骤）
用户说：「字段 X 不用了，改成字段 Y，帧头也改。」
AI 按流程 C **追加**变更记录，更新基线为 v2：
```markdown
## 当前生效基线（v2，2026-02-20）
- 需求点: 解析帧增加字段 Y（替代 X）；帧头格式改为 B

## 变更记录
### 变更 2 ｜ 2026-02-20 ｜ 用户
- 改成什么: 字段 X→Y，帧头改为 B
- 为什么: 现场反馈字段 X 无意义，换 Y；帧头格式升级
- 影响: 解析逻辑、上报逻辑、协议文档
- 被取代: 变更 1（2026-02-19）
```
→ 变更 1 保留在记录区，**未覆盖**（ADR 只追加）。

### 3. 变更前对齐拦住旧需求
新会话开始，AI 若只记得上次是「字段 X」，但先读基线看到 v2 是字段 Y
→ 不会基于旧需求写代码 ✅

### 4. 中途插入临时小需求（0002-登录超时修复）
用户说：「先帮我修个登录超时的 bug。」
- 在索引登记 0002，建独立目录 `reqs/0002-login-fix/`。
- 0002 与 0001 上下文隔离，互不污染。
- 需求 0002 的目录与上下文独立于 0001；当前 Git 分支保持不变，0001 的 TODO 进度原样保留。

### 5. 切回原需求
临时需求做完 → 重新选择需求 ID `0001` → 重新读索引 + REQS.md v2。
0001 的 TODO 仍显示「阶段 1 未完成」，进度未丢 ✅

## 需求上下文实证（分支保持不变；在隔离临时 git 仓库实测通过）

- 选择 0001：只加载 0001 目录，0001 TODO 进度保留；不加载 0002 的历史。
- 选择 0002：只加载 0002 目录，0002 的进度保留；Git 分支不因需求选择而切换。

## 关键结论
- **变更只追加**：需求历史完整、可回溯，AI 动工前核对基线防"基于旧需求写代码"。
- **按需求切分 + 分支仅记录**：多需求并行、中途插入/切换都不丢进度、互不污染，人工按实际开发需要决定是否切分支。
