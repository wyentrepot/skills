# req-mgmt — 需求/进度管理 playbook

> 适用：公司项目分支多、临时小需求与大需求并存、AI 开发时需求频繁变更后混乱的场景。
> 本 playbook 只描述**流程与交互规范**（遵循本技能目录中的 DECISIONS.md；每次会话只加载当前需求上下文），不含领域常量。

## 核心理念

1. **决策/需求只追加、不覆盖**（ADR 模式）：需求基线只存当前生效版本；每次变更追加一条记录，禁止静默覆盖。防止需求前后矛盾、AI 基于旧版本写代码。
2. **多需求切分 + 上下文隔离**：同一项目多个需求并存时，每个需求独立目录，互相不污染，可灵活切换。
3. **DECISIONS.md 设上限（满 10 条归档重启，3 缓存+7 新增）**：ADR 记录**含已被取代的**累计到 **10 条**即归档（`archives/`），新文件**复制原 #8/#9/#10 重排为 #1/#2/#3 缓存**、从 #4 起继续新增，每个生命周期=「3 条缓存 + 最多 7 条新增」。堆积有上限，历史不丢失，技能上下文不因归档而失忆（详见「G. DECISIONS.md 归档重启」）。
4. **计划单一来源**：`REQS.md` 管需求基线，`TODO.md` 管交付/阶段状态；需要多步实现时，必须调用 `writing-plans`，并将其完整计划写到同一需求目录的 `PLAN.md`。细粒度实现步骤和复选框只存在于 `PLAN.md`，不得复制到 `TODO.md`。

## 目录结构（项目内嵌）

```
reqs/
  0001-<需求slug>/          # 每个需求一个目录（ID 自增，slug 用英文短横线）
    REQS.md               # 该需求基线（只存当前生效版本）+ 变更记录（只追加）
    PLAN.md               # 当前生效基线对应的细粒度执行计划（由 writing-plans 生成）
    TODO.md               # 该需求的交付/阶段状态（不重复 PLAN.md 的实现步骤）
    DONE.md               # 该需求的完成日志（只追加，最新在上）
REQS-INDEX.md             # 项目级索引：所有需求 + 状态 + 关联代码分支（仅记录）
```

> 每个需求记录一个关联 git 分支，但分支不驱动需求上下文，也不要求随需求切换；需求目录与进度记录独立保存。

## 核心流程

### A. 会话开始（定位需求）
1. 读 `REQS-INDEX.md`，明确本次要处理的需求 ID，并读取其关联代码分支（仅作记录）。
2. 若本次需求尚未登记 → 判断是"临时小需求"还是"新大需求"，按需新建 `reqs/<id>/` 并在索引登记；不要通过切换 git 分支来选择需求。
3. **只加载当前需求的上下文**（`REQS.md`、`TODO.md`、`DONE.md`，以及存在时的 `PLAN.md`），不把其他需求历史灌进来。

### B. 开发前对齐（关键防混乱步骤）
1. 读当前需求的 `REQS.md`，核对**当前生效基线版本**（看最新变更记录）。
2. 若用户口头需求与基线不一致 → 先走「C. 需求变更」，再开发。
3. 若需求需要多步实现 → 调用 `writing-plans`，把其计划写入本需求目录的 `PLAN.md`。计划开头必须标注所依据的 `REQS.md` 基线版本；`PLAN.md` 是唯一的细粒度步骤、文件改动与验证命令来源。
4. 若本需求存在 `PLAN.md`，检查其标注的基线版本是否等于当前基线；不相等或计划标为失效时，不得执行该计划，必须重新调用 `writing-plans`。
5. 确认基线，以及多步实现所需的当前计划后才开始写代码。小且明确、不需要多步计划的需求可在核对基线后直接推进。**绝不在未核对基线的情况下动工。**

### C. 需求变更（只追加，不覆盖）
1. 在 `REQS.md` 的变更记录区末尾**追加**一条：
   ```
   ### 变更 N ｜ YYYY-MM-DD ｜ 变更人
   - **改成什么**: <一句话>
   - **为什么**: <原因>
   - **影响**: <涉及文件/分支/其他需求>
   - **变更前基线**: <版本号/提交号/可恢复快照位置>
   - **变更后基线**: <版本号/提交号/可恢复快照位置>
   - **被取代**: 变更 N-1（若覆盖上一版）
   ```
2. 先在记录中保留变更前后的版本号、提交号或可恢复快照/完整 diff，再更新顶部基线为最新版本，**正文旧内容保留在记录区**。
3. 若影响其他需求，在该需求记录区追加交叉引用说明。
4. 若变更影响范围、接口、验收标准或实现路径，且存在 `PLAN.md`，在其中标明“失效（基线 <旧版本>）”；不得继续执行旧计划。基线更新后重新调用 `writing-plans` 生成当前版本的计划。`REQS.md` 保留需求历史，`PLAN.md` 只保存当前可执行计划。

### D. 计划、任务与进度
- `PLAN.md`：只由 `writing-plans` 生成或更新，记录当前基线下的文件级实现步骤、前置失败检查、验证命令、依赖与回滚处理。执行时仅勾选这里的细粒度步骤。
- `TODO.md`：阶段化（`## 阶段` + `- [ ] 交付结果`）。大需求按交付里程碑分阶段，临时小需求单阶段即可；每个阶段可链接到 `PLAN.md`，但不得重复其实现步骤或测试命令。
- 一个 `PLAN.md` 阶段的验证全部通过后，才勾选对应 `TODO.md` 交付项；全部完成则把结果追加到 `DONE.md`（最新在上）。

### E. 多需求切换
1. 切换需求前，先确认当前需求的 `TODO.md` 交付状态，以及存在时的 `PLAN.md` 复选框已保存（未完成项原样保留）。
2. 直接按需求 ID 重新读取对应目录的 `REQS.md`、`TODO.md` 与存在时的 `PLAN.md`；关联 git 分支只在索引中记录，不执行自动 `git checkout` / `git switch`。
3. 切换只换需求上下文，双方进度独立保存，随时切回；若人工确需切分支，由人工自行把握并另行记录。

### F. 完成
- 需求完成 → 若存在 `PLAN.md`，确认其验证均通过；在 `REQS-INDEX.md` 把该需求状态改为「✅ 已完成」，并将完成结果追加到 `DONE.md`。

### G. DECISIONS.md 归档重启（满 10 条触发）
> ADR 记录（`### #N` 条目，**含已被取代的**）累计到 **10 条**时执行。归档是 DECISIONS.md **唯一合法的瘦身方式**，任何时候禁止直接删减正文。

1. **计数**：`grep -c '^### #' DECISIONS.md`。等于/超过 10 → 触发归档。
2. **归档**：把当前 `DECISIONS.md` 整份移到 `archives/DECISIONS-YYYYMMDD-HHmm.md`（建议同时 git 提交，历史永久可回溯）。
3. **重启（3 条缓存 + 7 条新增，防失忆）**：新建 `DECISIONS.md`，**复制当前文件的最后 3 条（#8、#9、#10）作为缓存种子**，依次重排为新文件的 **#1、#2、#3**（正文原样保留）；**不复制其余记录**。
4. **继续**：新文件从 **#4** 开始追加新决策；每次完成第 **10** 条记录后，立即先执行 dry-run，再直接执行 `--apply`，无需人工确认。每个生命周期=「3 条缓存 + 最多 7 条新增」。
5. **校验**：归档完成后运行 `node <req-mgmt>/scripts/validate.js`（检查技能产物完整）；`validate.js` 的校验范围保持为技能包本身。

> 归档后历史仍在 `archives/`，随时可回查；新文件永远带着最近 3 条决策开场，技能上下文不因归档而丢失。

## 交互规范
- AI 动工前必须执行 B（核对基线）；未核对就写代码属违规。
- 需求变更必须追加记录，禁止静默改写基线正文。
- 多步实现的细粒度计划只由 `writing-plans` 维护在当前需求目录的 `PLAN.md`；`TODO.md` 只记录交付状态。
- 计划的基线版本不匹配或已失效时，必须先重新规划，不得继续执行。
- DECISIONS.md 累计满 10 条 ADR 必须触发「G. 归档重启」；禁止用删减正文代替归档。
- 每次会话结束前，若有进度变化则更新 `TODO.md`、存在时的 `PLAN.md`、`DONE.md` / `REQS-INDEX.md`。
- 模板见 `templates/` 目录。

## 辩解表（AI 绕过流程的借口 → 现实）

> 违反字面即违反精神：以下借口都是绕开流程的合理化，一律不成立。

| AI 的借口 | 现实 |
|----------|------|
| 「这个变更很小，不用走变更记录吧？」 | 与大小无关，任何基线变更都必须追加记录；小变更最容易被后续忽略，更要留痕。 |
| 「REQS.md 我看过一遍了，基线没变，直接写」 | 核对基线是动工前动作，不是凭记忆；用户口头需求与基线不一致时必须先走流程 C。 |
| 「先写代码，回头补记录」 | 回头补 = 大概率不补；先追加变更记录再动工，顺序不可颠倒。 |
| 「旧需求本来就这么写的，沿用就行」 | 旧需求可能是已被取代的旧版本；只看最新变更记录所定的**当前生效基线**。 |
| 「这需求不在 REQS-INDEX 里，直接做吧」 | 不在索引 = 未登记；先建目录并登记（流程 A），否则进度无处保存。 |
| 「DECISIONS.md 太长？我把旧记录删掉就行」 | 删 = 违反只追加铁律；**必须走流程 G 归档重启**（归档进 `archives/`，历史不丢）。 |
| 「才满 10 条，我直接在新记录里覆盖旧的」 | 覆盖旧记录正文属于违规；第 10 条记录完成后立即执行流程 G 的 dry-run 并直接 `--apply`，新文件只缓存末尾 3 条。 |

## Red Flags（动工前自检，任一命中即 STOP）

- [ ] 我核对了 REQS.md 的**当前生效基线**（不是记忆中的版本）？
- [ ] 用户口头需求与基线不一致时，我走了流程 C 追加变更记录？
- [ ] 该需求已在 REQS-INDEX.md 登记、目录已建？
- [ ] 这是否为多步实现；若是，我是否已经用 `writing-plans` 生成当前需求目录的 `PLAN.md`？
- [ ] `PLAN.md` 依据的基线版本是否等于 `REQS.md` 的当前版本，且未被标为失效？
- [ ] 我是否把 PLAN.md 的文件级实现步骤、测试命令复制进 TODO.md，造成两份清单漂移？
- [ ] 切换需求前，当前需求的 TODO.md 进度已保存？
- [ ] 我正要静默改写基线正文或删除历史变更记录？
- [ ] DECISIONS.md 的 ADR 记录（含被取代的）已到 10 条却还没走流程 G 归档重启？
- [ ] 我打算用「删减 DECISIONS.md 正文」来瘦身，而不是归档重启？
