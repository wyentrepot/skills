# 知识库入库蒸馏（knowledge-manage）

## 触发与边界

- **触发**：新源文档入库蒸馏；补蒸存量文档；蒸馏卡修订/重拆；总索引、README、vault-map 等库级数据维护。
- **边界**：查库回答协议问题 → `knowledge-lookup`；CCO 代码移植/落点 → 库内 `CCO实现逻辑/SKILL.md`（cco-distill）。本技能的一切产出都是对库的变更，必须走 git。

## 动笔前必读（库规则三件套）

1. 库路径：`/01-workfile-ai/04-obsidian/obsidian`（其他环境按实际挂载替换）
2. `README.md`：双层分离原则——**协议层卡答"这帧怎么长"，业务层卡答"这业务怎么跑"**；卡结构 `frontmatter+概述+正文+来源+关联`
3. 库内 `_meta/vault-map.md`（与 lookup 共用，随库 git 管理）：库图/同义词/分诊规则
4. 库内 `tools/rebuild_index.py`：索引与卡维护工具（build / --check / --fix-aliases / --toc / --deprefix）

## 六步流程

### 1. 解析源文本
- PDF：`pdftotext`/`pypdf` 转文本，保留 `===== PAGE n =====` 分页标记，存 `/tmp/<名>.txt`
- 通读全文，建立「功能/章节清单 + 页码-行号映射」，再决定拆卡
- ⚠️ OCR/文字流提取会把位域表粘连成一行：位域字段宽度和字节归属必须按原 PDF 列坐标重建，或与已有卡互证，不得照抄粘连文本

### 2. 拆卡规划（一功能一卡一责）
- 有帧格式/数据单元/位域 → **协议层卡** `协议层/NN_<主题>_帧格式.md`
- 有业务流程/参与方任务/方案 → **业务层卡** `业务层/NN_<主题>_业务.md`
- 同一功能的协议+业务卡成对撰写并互链；纯规范类（技术/型式/检验规范）不强行编帧结构
- 编号：接全库现有最大号递增（先 `ls 协议层 业务层 南网/协议层 南网/业务层` 查最大值并 **grep 查重**——历史上已有跨目录重号，如 协议层/70_安徽 与 南网/协议层/70_总则，新卡不得再重号）
- 大文档（多功能手册）按功能拆多对卡，小文档可一源一卡；产出文件清单定下来再动笔

### 3. 子代理分发（批量 ≥4 张卡时）
- **并发 ≤2**，分批串行；失败（captcha/cancel/concurrency）原样重发
- 每个代理提示词必须自包含：①两张格式样例卡路径（业务卡 `业务层/38_河南HPLC模块协议_业务.md`、协议卡 `协议层/10_QGDW10376.2_帧格式.md`）②源文本 Read offset/limit 区间 ③内容要点索引（声明"仅索引，源文本是唯一权威"）④下述硬性规则 ⑤汇报格式（每文件一行：路径+摘要+协议落点）
- 代理只写自己名下的文件，禁止动索引（主会话统一改，避免冲突）

### 4. 写卡硬性规则
- **忠于源文本**：数字/默认值/字节长度/枚举逐项核对，不编造不遗漏；两处矛盾如实标注，不圆场
- frontmatter：业务卡 `title/doc_type:"业务层-功能提炼"/source/scope/tags`；协议卡 `title/aliases/tags`（tags 含 `协议层/业务层, 国网, HPLC, 电科院手册, <功能词>`）
- 来源：有 ima md 版 → `[[ima/<库>/md版本/<文件>|原文]]` 双链；无（如本地 PDF）→ 纯文本 `来源：<文档名>（第X章/附录X）`，**禁止对不存在路径造双链**
- 正文：中文；`## 一、二、三`；ASCII 帧图代码块 + 字段表格，**枚举全量转出**（不写"等等"）
- `## 关联`：业务↔协议必互链，格式 `[[蒸馏/业务层/NN_..._业务.md|NN 中文标题]]`（沿用 `蒸馏/` 前缀惯例，lookup 按 basename 解析）；跨卡关联确有才加
- 卡是"蒸馏"不是"搬运"：概述→结构/流程→关键字段→注意事项收口，单卡超 ~30KB 应考虑再拆

### 5. 索引与库数据同步（每批入库后立即做，不许欠账）
- 固定命令序列（原样执行，顺序不可换）：
  `python3 tools/rebuild_index.py --fix-fields && python3 tools/rebuild_index.py --fix-aliases && python3 tools/rebuild_index.py --toc && python3 tools/rebuild_index.py`
  （补字段 → 补别名 → 大卡导航 → 重建总索引/README/vault-map 规模段）
- `_meta/vault-map.md`：为新功能/新来源手册**手动补同义词词条**（脚本只管规模数字；新卡若无任何词条提及，必须补）
- 库根 `经验索引.md`：蒸馏中的非显然发现（OCR 坑、协议歧义、跨文档矛盾）追加一行；协议口径矛盾另入 `CCO实现逻辑/13-文档与代码差异记录.md`

### 6. 校验与提交
- 校验：`python3 tools/rebuild_index.py --check`——断链=错误必须清零，缺字段/编号重号=警告酌情修；互链双向人工过一眼
- 提交：`git add` **仅限本次产物 + 索引/README/_meta**（用户未提交的其他改动一律不碰）；pre-commit 钩子会自动再跑一次 --check；提交信息 `蒸馏: <源文档名> → 业务层X-Y + 协议层A-B 共N张 索引更新`
- 汇报：卡清单表（卡号/功能/核心协议落点）+ 提交号 + 遗留问题（PDF 是否入库、存疑点）

## 常见错误

| 错误 | 修正 |
| --- | --- |
| 并发拉满子代理 | ≤2，分批串行，失败重发 |
| 位域表照抄 OCR 粘连文本 | 按 PDF 列坐标重建，与同族帧头互证 |
| 新卡编号与目录内已有卡重号 | 入库前查重；`--check` 也会拦 |
| 卡写完不跑 rebuild_index.py | 第 5 步强制，欠账即检索事故 |
| 凭"总索引说 62 卡"判断库规模 | 以 vault-map/实测 ls 为准，索引永远可能滞后 |
| 提交时顺带 add 用户其他未跟踪文件 | 只 add 本次产物 |
