# 工程代码修改约定与编码规范

---

## 一、C 代码修改约定

- **最小 diff**：以最小变更解决问题，不移动大块代码、不改无关文件缩进风格。
- **日志**：使用文件或模块内已有日志接口，不引入新的第三方日志库。
- **头文件**：沿用同目录或同模块已有 include 顺序；新增依赖时只加必要项。
- **可移植性**：尊重工程自定义类型宏（`UINT8`、`INT32U` 等）与 `__SLOWTEXT` 等属性，勿随意换成标准 `<stdint.h>`（除非该文件已统一使用）。
- **条件编译**：涉及配置宏的新代码路径，需在宏关闭时仍可编译或明确 `#if` 包裹。
- **修改后**：主动提示可运行的 make 目标。

---

## 二、C/C++ 嵌入式编码规范摘要（142 条）

- 本技能面向内部 C 工程，不执行语言版本迁移。
- 以项目现有编译选项和同文件既有风格为准，可兼容 C89 与工程已采用的 C99 写法。
- 修改时不得仅为统一 C89/C99 风格而改写无关代码；新增代码应与所在模块保持一致。

### 2. 文件规则（9 条）

- C 头文件用 `.h`，源文件用 `.c`；C++ 头文件用 `.h`/`.hpp`，源文件用 `.cpp`
- C 头文件和源文件名字一致（含大小写），只有扩展名不同
- C++ 文件名采用类名，禁止仅通过大小写区分多个文件
- C++ 每个类只能定义 1 个头文件和 1 个源文件
- 引用系统库头文件用 `<>`，其他头文件用 `""`
- 头文件引用顺序：系统库 → 第三方 → 自有
- 只包含需要的头文件，移除不再需要的
- 头文件必须有防止多次包含的保护（如 `#ifndef`）
- 头文件不要引用其他头文件，应在源文件中引用

### 3. 注释规则（7 条）

- 单行注释可用 `//` 或 `/* ... */`，多行注释用 `/* ... */`；具体形式与当前文件保持一致
- 文件必须以注释开始，包含版权、作者、简述等信息
- 作为接口的类或函数必须提供功能、参数、返回值注释
- 常量、全局变量、静态变量定义时必须带注释
- 注释要尽量靠近被解释的代码
- 注释掉的源代码必须删除，若需保留用条件编译
- 注释尽量用英文 **[建议]**

### 4. 格式规则（16 条）

- 每行代码不超过 80 字符，最多 100 字符；过长在逗号或操作符处拆行并对齐
- 每个函数代码行数不超过 200 行
- 每个文件代码行数不超过 2000 行（自动生成代码和资源文件除外）
- 每行只能写 1 条语句
- 缩进用 4 个空格
- 制表符(Tab)设置为 4 个空格
- `if`、`else`、`while` 等语句块内的代码要缩进 4 个空格
- 行尾不要遗留空格
- 指针声明：`*`/`&` 与类型连在一起，后面空格接变量（禁止前后都有空格）
- 一元操作符（`&`、`*`、`++`、`--`）与操作数之间无空格
- 逗号和分号后面接 1 个空格
- 二元操作符（`=`、`==`、`+`、`&&` 等）前后要有空格；但 `->`、`.`、`()`、`[]` 前后无空格
- 小括号：函数名与左括号无空格；语句中小括号外面留 1 个空格，里面与变量无空格
- 大括号：初始化列表、空类不独占一行；其他场景可独占或不独占，但需风格统一
- 函数参数：第一个参数与函数同行，空间足够则所有参数同行，不足则每个参数占一行并左对齐
- 函数代码过多时可划分多个代码区域，配合注释说明 **[建议]**

### 5. 命名规则（20 条）

- 匈牙利前缀规范：`u8`/`u16`/`u32`/`i8`/`i16`/`i32`/`f32`/`f64`/`b`(布尔)/`p`(指针)/`c`(char)/`str`(字符串)/`s_`(静态)/`g_`(全局)/`m_`(成员)
- 命名必须有明确含义，避免二义性
- 禁止仅通过大小写区分不同命名
- 有约定俗成的缩写时，用缩写代替全拼
- 命名缩写应避免歧义，否则用全拼
- 禁止以下划线开头
- 禁止用关键字（`bool`、`class`、`new` 等）命名
- 禁止用非英语（如汉语拼音）命名
- 命名长度不超过 4 个单词
- [C++] 类命名用 Pascal 规则，如 `ConnectPort`
- [C++] 接口命名以 `I` 开头后接 Pascal 命名，如 `IMyInterface`
- 枚举命名用 Pascal 规则，如 `FileMode`
- 函数命名用 Pascal 规则，如 `ConnectPort()` **[建议]**
- 函数参数命名用 Camel 规则，如 `portConnection` **[建议]**
- 局部变量命名用 Camel 规则，如 `portConnection` **[建议]**
- [C++] 成员变量用匈牙利规则，以 `m_` 开头，如 `m_member` **[建议]**
- 全局变量以 `g_` 开头，如 `g_isEnable` **[建议]**
- 静态变量以 `s_` 开头，如 `s_counter` **[建议]**
- 局部变量禁止与外部变量（全局、静态、函数名）重名
- [C++] 基类和派生类的非重载成员不能重名

### 6. 代码规则（50 条）

**6.1 通用（10 条）：**
- 违规必须标记，注释以 "Break rules" 开头
- 复用遗留代码时违规需标记，注释以 "Legacy Codes" 开头
- 第三方代码违规标记 "3rd Party Codes" 且不要修改
- C 函数实现不要放在头文件中
- [C++] 类成员函数实现不要放在头文件中（内联和模板除外）
- 能用库函数的禁止自行替代
- 少用宏定义，用常量、枚举、内联函数替代 **[建议]**
- 代码优化原则：先正确 → 测效率 → 再优化，每次优化后要测试
- 优化优先依赖编译器的优化选项
- 代码标识符用英文字符（字符串内容除外）

**6.2 变量（6 条）：**
- 所有变量（含指针、数组）使用前必须明确赋值
- 枚举的每个成员必须明确赋值
- [C] 头文件不要初始化变量，应在源文件中初始化 **[建议]**
- 少用全局变量，多用局部变量 **[建议]**
- 外部用不到的全局变量声明为 `static`
- 常量全部大写，多单词用下划线连接

**6.3 语句（17 条）：**
- 用常量 / 枚举代替数字（0 除外）
- 数组或内存分配尽量用常量代替 "魔数" **[建议]**
- 禁止对常量进行类型转换
- `if` / `while` 等后的语句块必须用 `{}` 明确作用域
- 计算逻辑复杂时用小括号明确优先级
- 小括号嵌套不超过 5 层，超过应拆分
- `++` 和 `--` 不要与其他操作符混用在一个语句中
- 注意前置 / 后置递增递减的区别以及 `&&` / `||` 的短路特性 **[建议]**
- `switch` 必须有 `default` 分支
- `case` / `default` 分支必须有 `break` 或 `return`，否则注释 "fall through"
- 空指针使用 `NULL`，不要用 0 表示空指针
- 不要将指针强制转为整型；C89 没有标准 `uintptr_t`，确需转换时必须使用工程明确提供且能容纳指针的无符号类型，并说明编译器依赖
- 避免 "指针的指针"，可用结构或类替代
- 操作数组或容器下标前必须检测是否越界
- 长整型常量后缀用大写 `L`，不用小写 `l`
- 用 `typedef` 定义函数指针，不直接定义 **[建议]**
- 死代码必须移除

**6.4 函数（17 条）：**
- 函数参数类型尽量一致（如都用常引用） **[建议]**
- 参数顺序：先输入参数，后输出参数
- 输入参数必须用 `const` 常量化
- 输出参数禁止 `const` 常量化
- 传参用指针或引用代替值传递；复杂数据结构必须用指针 / 引用
- 公有 / 全局函数参数不超过 5 个，否则拆分
- 函数内嵌套不超过 5 层，否则重构
- 文件内部不被外部调用的函数声明为 `static`
- 少用 `goto`，用 `return`、`break`、`continue` 替代 **[建议]**
- 禁止函数递归调用，用递推算法替代
- [C++] 用 `static_cast` 等转型代替强制转换操作符 **[建议]**
- 宏定义函数的每个参数和整个表达式必须加括号
- 少用全局数据或共享数据 **[建议]**
- 操作全局 / 共享数据时要用互斥锁保护
- 不要滥用互斥锁：每个临界区尽量只用 1 把锁，代码要小而短
- 可重入函数禁止使用全局 / 静态数据
- 必须检查并处理函数返回的错误信息 **[建议]**

### 7. C++ 类规则（21 条）

- 不要轻易构建基类，应从现有成熟类派生
- 派生类体系中最顶层的基类应为抽象基类
- 禁止使用多重继承和菱形继承
- 不要在头文件中写 `using namespace`
- 源文件中 `using namespace` 应放在所有 `#include` 之后
- 类成员（变量和函数）尽量私有/保护，不要公有化
- 重载操作符：重载二元操作符时也要重载对应的一元操作符；重载 `=` 时检查自赋值；尽量返回常引用
- 调用全局函数时用 `::` 明确（如 `::GlobalFoo()`）
- 成员函数避免返回指针或引用，应返回对象或值
- 成员函数返回成员变量时返回常量的，避免被外部修改
- 抛出异常时直接抛对象，不要抛指针或引用
- 静态成员变量应用静态成员函数来操作 **[建议]**
- 成员函数如果能被 `const` 化，就加上 `const` **[建议]**
- 构造函数用成员初始化列表，而不是在函数体内赋值
- 多态时禁止将基类强制转为派生类（反之可以）
- 类成员变量不超过 20 个，否则拆分为多个类
- 用 `class` 代替 `struct`（封装更好）
- 用 `std::vector` 代替普通数组
- 用迭代器遍历 `vector`，不要用传统 `for` 循环
- 用智能指针代替普通指针
- 代码尽量保持简单明了，可读性优先于执行效率

### 8. 错误和异常规则（6 条）

- **8.1 异常处理策略 `[建议]`**：尽量避免或控制崩溃；必要时进入安全降级状态；使用冗余防护；记录足以定位问题的错误上下文。通过返回码、状态码和错误处理分支处理运行错误。
- **8.2 不要忽略异常或错误 `[强制执行]`**：必须检查并处理返回码、错误标志、空指针和异常状态；禁止静默吞掉错误或隐藏失败状态。
- **8.3 对异常或错误进行处理 `[强制执行]`**：仅记录日志不等于完成处理；应按场景向调用者返回错误、回滚、重试、降级或进入安全状态。
- **8.4 异常处理需要正确释放资源 `[强制执行]`**：异常或错误处理路径必须释放所有已成功获取的动态内存、文件句柄、套接字、锁和其他系统资源；释放顺序应与获取顺序相反，任何提前返回或跳转都不得绕过清理。使用统一清理出口或等效机制，确保部分初始化路径也能正确释放资源。
- **8.5 避免指针引发的异常 `[强制执行]`**：指针定义时必须初始化；无有效目标时使用 `NULL`；解引用或传入要求非空的接口前必须判空；释放资源后必须立即置空，避免悬空指针、重复释放和释放后使用。
- **8.6 嵌入式系统中的异常防护 `[建议]`**：按系统能力采用看门狗、栈保护、Flash 校验和及受控的异常中断处理；异常中断会增加定位难度，只在必要时使用。

### 9. 嵌入式规则（13 条）

- 设计硬件抽象层(HAL)和操作系统抽象层(OSAL)隔离软硬件，便于移植 **[建议]**
- 优先使用工程已定义的定长类型（如 `UINT8`、`INT32U`）；所在模块已统一使用 C99 标准类型时可沿用 `<stdint.h>`
- 优先选整型，避免浮点；需浮点时扩大为整数处理
- 除需要负数外，优先用无符号类型
- 禁止对有符号整型执行移位操作
- 操作数组下标前必须先检测范围
- 用单精度浮点(`float`)替代双精度(`double`)，用后缀 `F` 明确
- 使用所在模块和工具链已支持的单精度数学接口（如 `sinf()`）；资源受限场景优先考虑定点或整数算法
- 类型转换时明确写明转换后的类型
- 用静态内存分配，避免动态分配（`malloc`/`free`） **[建议]**
- 使用动态分配时必须用完释放并置空指针
- 常量用 `const` 常量化，节省 RAM，防止修改
- 以下情况用 `volatile`：与硬件关联、被中断/多线程操作、直接读写硬件寄存器
